# 需求、建议与待验证事项

## 已由用户确认

1. 开发类似 macOS 体验的操作系统，底层采用 Linux。
2. 可以复用 Linux 的驱动和底层生态，但建立自己的应用平台。
3. 图形界面追求高性能、流畅动画和丰富效果。
4. 应用优先使用 Kotlin 等高级语言开发。
5. 应用获取外部系统能力只能通过 SDK 开放接口，不能任意调用底层系统。
6. 先整理讨论并写入文档，然后开发第一步：Ming App Host、Kotlin 测试应用、授权文件读取和越权拒绝。

7. 每个阶段完成并验收后直接进入下一阶段，持续推进到可验收系统或真实外部阻碍。
8. 2026-10-24确认：采用真正的Compose编程模型，再配MingOS组件；使用真实Compose Compiler/Runtime，平台组件与后端通过Ming SDK接入。编译、重组、销毁及wasmWasi兼容性需实际验证。

9. 2026-10-24同意重新比较JVM/ART与Wasm；真正Compose编程模型已确定，正式应用运行时暂未迁移，结论要结合真实探针和SDK隔离设计。

10. 2026-10-24最终明确：放弃JVM路线，继续Kotlin/Wasm/WASI与Wasmtime；真正Compose Compiler/Runtime通过官方源码平台适配接入MingOS组件。JVM探针仅保留历史对照，不迁移正式运行时。

## 架构解释

“SDK-only”限制面向应用的外部能力，并不禁止纯计算、语言运行时内部实现。宿主和系统服务必然调用底层系统；它们属于平台实现，不能与普通应用混为一谈。应用自身、第三方依赖和原生扩展都必须受同样边界约束。

SDK 包装和开发工具检查不能独立构成安全边界。需要受控运行时、服务端授权，以及最终 Linux 上的进程、文件系统、网络、系统调用及资源隔离。

## 建议，尚不是用户已确认的承诺

- 先限定一种架构、一款真实硬件和一个 Linux 测试环境。
- 采用 Wayland 桌面；原生合成器负责全局窗口管理和效果。
- 保持当前Kotlin/Wasm受控接口；真实Compose编程模型已由用户确认，Runtime平台适配与现成UI组件兼容范围仍需验证，已排除普通JVM应用主线。
- Shell、图形、文件等按权限和故障边界拆分，避免把每个 SDK 方法都变成一次 IPC。
- 建立 Ming UI、开发工具、应用包、版本兼容和更新恢复机制。

## 尚未确定

目标用户和首批任务；x86-64 或 ARM；GPU 与硬件名单；Linux 基础系统；Compose/Wasm生产适配方式及组件兼容范围；应用商店及分发渠道；项目团队规模；系统 ABI 稳定承诺；最终内核隔离策略。

## 第一阶段范围

包括：文档、原型宿主、SDK v0、Kotlin/Wasm 示例、授权测试、资源超时、运行说明与测试记录。

不包括：自有内核、启动镜像、Wayland 合成器、完整 UI 框架、图形性能达标证明、生产沙箱、应用商店、系统更新。宿主的 Windows 验证不能替代 Linux 安全验证。
